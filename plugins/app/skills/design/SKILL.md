# /gapp:design — 디자인 결정 세션

목표: "그때그때 물어보는 디자인"을 없앤다. 여기서 결정을 전부 확정해 **tokens + DESIGN.md**로
굳히면, 이후 모든 화면 작업은 문서를 따르기만 하면 된다.

## 출력 언어

사용자와의 대화 — 진행 보고, 요약, 체크리스트/판정 표, `AskUserQuestion`의 질문·헤더·옵션·설명 — 은 **한국어**로 쓴다. 하위 에이전트를 띄울 때도 결과가 사용자에게 그대로 노출되는 텍스트는 한국어로 돌려달라고 프롬프트에 적는다.

영어 그대로 두는 것: 코드·식별자·파일 경로·명령어·환경변수·워크플로 YAML·스킬/툴 이름, 고정 라벨과 상태 키워드(`PASS`/`FAIL`/`SKIP`, `✅`/`⚠️`), 그리고 커밋 메시지·브랜치 이름·PR 제목/본문 — 이건 대상 레포의 기존 관례를 따른다.

**앱 산출물은 이 규칙이 아니라 `kickoff`에서 정한 앱 언어(`docs/HARNESS.md`)를 따른다.** 앱 UI 문구, 랜딩 카피, 개인정보/지원 페이지, 스토어 메타데이터·스크린샷 문구는 전부 앱 언어로 — 영어 앱에 한국어 스토어 메타데이터를 넣지 않는다.

사용자가 다른 언어로 요청하면 그 언어를 따른다.

## 0. 디자인 스킬 확보 (없으면 설치 유도)

사용 가능한 스킬 목록에서 확인하고, 없으면 유저에게 설치를 권한다 (설치는 유저 확인 후):

| 스킬 | 용도 | 설치 |
|---|---|---|
| `design-consultation` (gstack) | 프로덕트 이해→랜드스케이프 리서치→디자인 시스템 제안+폰트/컬러 프리뷰 생성. **있으면 1단계(방향 결정)를 이 스킬에 위임**하고, 그 결과를 2단계에서 토큰화한다 | gstack 설치 시 포함 |
| `mobile-app-ui-design` | 모바일 화면/플로우/컴포넌트 설계 본체 | `npx skills add ceorkm/mobile-app-ui-design` |
| taste 계열 (`design-taste-frontend`, `high-end-visual-design`, `minimalist-ui` 등) | 미학 방향·AI슬롭 회피 | `npx skills add Leonxlnx/taste-skill` (여러 스킬 일괄) |
| `frontend-design` (Anthropic 예제) | 의도적 시각 디자인 일반론 | 플러그인 마켓플레이스 |

설치 후 프로젝트에 `skills-lock.json`이 생기는 방식(npx skills)이면 커밋한다.
하나도 설치 못 하는 환경이면 스킬 없이 진행하되, 그 사실을 유저에게 알린다.

## 1. 방향 결정 (유저와 함께, AskUserQuestion)

kickoff의 "디자인 방향" 메모(레퍼런스/무드 키워드)에서 출발한다. 결정할 것:

1. **미학 방향 1개** — 후보 2~3개를 *구체적 차이가 보이게* 제시 (예: "필름 다이어리 — 따뜻한 종이
   질감, 세리프 헤드라인" vs "클리니컬 미니멀 — 순백, 모노 숫자"). taste 스킬이 있으면 로드해서
   후보의 질을 올린다.
2. **타이포그래피** — 헤드라인/본문/숫자 폰트. **한국어 앱 필수 규칙: 시스템 폰트 폴백 금지**
   (한글 글리프가 깨진다). 한글+라틴 커버 폰트(예: Pretendard)를 expo-font로 정적 웨이트 번들.
   숫자/라벨용 모노 폰트는 선택.
3. **컬러 팔레트** — 배경/서피스/텍스트 위계/포인트/시맨틱(성공·경고). 라이트/다크 지원 여부를
   여기서 결정 (다크면: 순흑·순백 금지, inverse 토큰 별도).
4. **스페이싱/라운드/그림자 스케일**, **모션 원칙** (스프링 vs 타이밍, 화면 전환 방식).

**결정 방식:** 후보를 말로만 나열하지 말고, 가능하면 HTML 목업이나 이미지 생성 스킬
(`imagegen-frontend-mobile` 등 설치돼 있으면)로 **보여주고** 고르게 한다. 핵심 화면 1개
(피드/홈)의 목업으로 방향을 검증한 뒤 토큰화하는 순서가 실패가 적다.

## 2. 굳히기 — tokens + DESIGN.md

1. **`theme/tokens.ts`에 실값 채우기** — scaffold가 만든 골격에: `colors`, `typography`(폰트 패밀리
   상수 포함), `spacing`, `radius`, `shadow`, `withOpacity()`. 폰트 파일 번들 + `expo-font` 로드 코드,
   웹 타깃이면 웹 폰트 주입 함수까지.
2. **`DESIGN.md` 생성** — 미학 이름과 원칙(3~5개 규칙, 위반 예시 포함), 타이포 위계표, 컬러 의미표,
   "하지 말 것" 목록 (예: 인라인 hex 금지, 시스템 폰트 폴백 금지, 수동 rgba 금지 — withOpacity 사용,
   다크면 순흑 금지). **규칙 #1은 가장 깨지기 쉬운 것**으로.
3. 첫 화면 1개를 토큰만으로 스타일링해 룩이 실제로 나오는지 검증.

## 3. 마무리

- HARNESS.md: design 체크, "디자인 방향" 섹션에 확정 미학 한 줄 + DESIGN.md 링크, 로그.
- 확정 요약 한 줄 보고 후 **다음 단계를 바로 이어서 실행한다** (이어달리기 규칙):
  백엔드 필요 시 `/gapp:backend`, 아니면 `/gapp:cicd`.

## 피할 것

- 유저 취향 확인 없이 "무난한" 팔레트로 자체 결정 — 이 단계의 존재 이유가 취향 확정이다.
- 토큰 없이 화면부터 만들기 — 나중에 전 화면 재작업이 된다.
- 다크모드를 "나중에" — 지원 여부만이라도 지금 결정 (토큰 구조가 달라진다).
