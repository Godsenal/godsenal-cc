# /gapp:landing — 랜딩 사이트 + 스토어 제출 전제물

App Store 제출에는 **개인정보처리방침 URL이 필수**고 지원 URL도 사실상 필요하다. 이 스킬은 그
전제물을 겸하는 마케팅 사이트를 만든다. 화려할 필요 없다 — v1은 정적 페이지면 충분.

## 1. 구조 결정 (기본값으로 진행, 특이 요구만 확인)

- **위치: 앱 모노레포의 `web/` 하위** (기본). 별도 레포는 관리 포인트만 늘린다 — 실제로 별도 레포로
  갔다가 모노레포로 회귀한 전례가 있다.
- **스택: 정적 HTML/CSS 우선.** 페이지 3~4장(홈/개인정보처리방침/지원/이용약관)에 프레임워크는
  과투자. 앱이 웹 버전을 가질 때만 Next.js 등 고려.
- **배포: Vercel** — 프로젝트를 앱 레포에 연결하고 **Root Directory를 `web`으로** 지정.
  `vercel.json`에 `cleanUrls: true`를 쓸 경우 **rewrite `dest`에 `.html`을 붙이지 마라**
  (붙이면 리다이렉트 루프/404 — 실사고).
- CI 무관: Vercel Git 연동이 web/ 변경에 자동 반응. 앱 CI(`ci.yml`·`eas-update.yml`)의
  paths-ignore에 `web/**`가 있는지 확인(cicd 단계에서 안 했으면 지금 추가).

## 2. 페이지 구성

- **홈**: 앱 한 줄 정의(HARNESS.md에서), 스크린샷 1~2장(store-assets 이후면 재사용), 스토어 배지
  자리(출시 전엔 "Coming soon"), 지원 이메일. **DESIGN.md의 토큰(색/폰트)을 웹에도 적용** —
  앱과 사이트가 같은 브랜드로 보여야 한다.
- **개인정보처리방침** (`/privacy`): 실제 수집 항목 기준으로 작성 — backend 유무에 따라 다르다
  (로컬 전용이면 "수집하지 않음" 중심, Supabase면 계정/콘텐츠/식별자 명시). 앱 언어와 동일 언어로.
  store-assets의 메타데이터 문서와 내용이 일치해야 한다.
- **지원** (`/support`): 문의 이메일 + FAQ 두어 개. **개인 이메일 노출 주의** — 전용 주소를 쓰고,
  공개 페이지에 실명 개인 계정을 박지 않는다 (교체 커밋 전례 있음).

## 3. 배포 + 검증

1. Vercel 프로젝트 생성/연결 (Root=web) → 배포.
2. 프로덕션 URL 3개(홈/privacy/support)가 실제로 200 뜨는지 확인 — 특히 cleanUrls 환경에서
   `/privacy` 직접 진입.
3. 커스텀 도메인은 선택사항 — vercel.app 서브도메인으로도 심사 통과에 문제없다.

## 4. 마무리 + 이어달리기

- HARNESS.md: landing 체크, **privacy/지원 URL을 결정사항에 기록** (store-assets가 그대로 쓴다), 로그.
- 이어달리기 규칙에 따라 다음 단계로: 출시 준비가 목적이면 `/gapp:store-assets`를 바로 이어서 실행,
  아직 개발 단계면 개발 루프로 복귀한다고 한 줄 보고.
