# /gapp:kickoff — 아이디어 → 앱 하네스 시작

새 앱을 만들 때마다 같은 것을 놓치지 않기 위한 파이프라인의 **0단계**다. 이 스킬의 산출물은 코드가
아니라 **결정과 문서**다: 아이디어를 오피스아워식으로 두들겨 보고, 확정된 결정을 `docs/HARNESS.md`에
적고, 곧바로 다음 단계로 이어달린다.

## 전체 파이프라인 (이 스킬이 관장하는 지도)

```
0. kickoff      아이디어 인터뷰 + 결정 확정 + HARNESS.md 생성   ← 지금 여기
1. scaffold     Expo 환경세팅 (최신 SDK, 컨벤션, CLAUDE.md)
2. design       디자인 결정 세션 (taste/mobile-ui 스킬) → tokens + DESIGN.md
3. backend      Supabase 백엔드 (보안모델, 마이그레이션 규율)     [백엔드 필요 시]
4. cicd         GitHub Actions + EAS 파이프라인
5. landing      마케팅/랜딩 사이트 + 개인정보처리방침 URL          [스토어 제출 전제물]
   ↳ 이후 개발 루프: 기능 개발 ⇄ 테스트 ⇄ deploy(OTA/빌드)
6. store-assets 스크린샷 + 스토어 메타데이터
7. store-submit preflight 게이트 통과 후 Claude Chrome으로 ASC 제출
```

### 이어달리기 규칙 (모든 gapp 스킬 공통)

**단계가 끝나면 멈추지 않는다.** HARNESS.md를 갱신하고 한 줄 보고한 뒤, 유저가 멈추라고 하지 않는 한
다음 단계 스킬을 **곧바로 이어서 실행**한다. "다음에 뭐 할까요?"라고 묻고 대기하는 것 금지 — 유저가
명령을 다시 쳐야 진행되는 하네스는 실패작이다. 멈추는 지점은 유저 입력이 실제로 필요한 곳
(취향 선택, 계정/시크릿, 비용 발생, 되돌리기 힘든 트리거)뿐이다. 세션이 끊겨도 `HARNESS.md`만 있으면
`/gapp:next` 한 방으로 이어진다.

## 1부 — 오피스아워 인터뷰

**먼저 `office-hours` 스킬(gstack)이 설치돼 있는지 확인하라.** 있으면 아이디어 검증·구체화는 그쪽에
위임하는 게 낫다 — 수요 실재성·현상유지 비용·최협 웨지 같은 포싱 질문이 훨씬 정교하다. 위임한 경우
이 스킬의 역할은 그 결과를 아래 A~E 결정 영역으로 수렴시켜 HARNESS.md로 굳히는 것. 없으면 아래
방식으로 직접 진행한다.

**진행 방식이 핵심이다.** 설문지처럼 질문을 쏟아내지 말고, 오피스아워 파트너처럼 행동하라:

- **한 번에 1~2개 질문만.** `AskUserQuestion`으로 선택지를 주되, 답을 듣고 나서 다음 질문을 정한다.
  앞 답변이 뒤 질문을 바꾼다 — 대본을 미리 다 짜지 마라.
- **동의 머신이 되지 마라.** 아이디어의 약점(누가 왜 쓰나, 기존 대안 대비 뭐가 나은가, 왜 지금인가)을
  솔직하게 찌른다. 단, 찌르는 목적은 죽이기가 아니라 **MVP를 깎는 것**이다.
- **스코프를 자르는 게 최대 기여다.** "v1에서 뺄 것" 목록이 "넣을 것" 목록만큼 길어야 정상.
- 유저가 이미 답을 정해 온 항목은 다시 묻지 말고 확인만 하고 넘어간다.
- **답할 수 있는 건 스스로 답하라.** 스택 버전·요금·규격처럼 조사로 알 수 있는 건 유저에게 묻지 말고
  조회해서 채운다. 유저에게 가는 질문은 유저만 답할 수 있는 것(취향·목적·예산)만.

커버해야 할 결정 영역 (순서는 대화 흐름에 맡기되, 끝났을 때 전부 채워져 있어야 함):

### A. 프로덕트
- 한 줄 정의: 누구의 어떤 문제를 어떻게 푸는가
- 타깃 유저 + 첫 10명을 어디서 구할 건가 (본인/지인용이면 그것도 유효한 답)
- v1 스코프: 코어 루프 하나만. 나머지는 전부 "이후" 목록으로
- 이름(가칭 OK), 번들 ID(`com.<owner>.<app>`), 언어(한국어/영어/다국어)

### B. 플랫폼/스택
- iOS / Android / 웹 중 v1 타깃. (기본 권장: **Expo + React Native**로 시작, 웹 랜딩은 별도)
- **스택 버전은 기억으로 정하지 마라.** 이 시점에 반드시 최신을 조회한다:
  - Expo 최신 SDK: https://docs.expo.dev/versions/latest/ 를 WebFetch (또는 context7)
  - 그 결과(SDK 번호, RN/React 버전)를 결정사항으로 기록 — scaffold 단계가 이 값을 쓴다
- 네이티브 기능 필요 여부(카메라, 위젯, Apple Sign-In, 푸시…) — dev client 필요성 판단에 직결

### C. 백엔드/데이터
- 로컬 전용으로 충분한가, 서버가 필요한가(공유/동기화/계정이 있으면 서버行)
- 서버가 필요하면 기본 권장: **Supabase** (backend 스킬이 보안모델까지 세팅)
- 로그인 정책: 익명 우선(로그인 마찰 제로) + 필요 시 승격 패턴을 기본 권장
- 과금 계획(없음/유료 앱/IAP) — 스토어 메타데이터와 심사에 영향

### D. 디자인
- 여기서는 **방향성만** 잡는다(레퍼런스 앱 2~3개, 무드 키워드, 톤). 구체 결정(타이포/컬러/토큰)은
  design 스킬이 taste 스킬들과 함께 진행한다고 안내.
- 한국어 앱이면 미리 경고: 시스템 폰트 폴백으로 한글이 깨지는 사고가 흔하다 → 번들 폰트 전제.

### E. 운영 전제 (미리 알려줄 것)
- Apple Developer 계정($99/yr) 필요 여부, EAS 빌드 크레딧, Supabase 무료 티어 한계
- 테스트 경로: 시뮬레이터 → TestFlight 내부 테스트(심사 없음) → 심사 제출
- 배포 경로 두 개(OTA vs 네이티브 빌드)가 있다는 것 — 자세한 건 deploy가 담당

## 2부 — HARNESS.md 생성

인터뷰가 끝나면 프로젝트 루트를 정하고(새 디렉토리면 여기서 mkdir + git init) `docs/HARNESS.md`를
생성한다. 이 문서는 **모든 gapp 스킬이 읽고 쓰는 단일 진실**이다.

템플릿:

```markdown
# <앱이름> — 하네스

> gapp 파이프라인 추적 문서. 각 스킬이 자기 단계 완료 시 체크하고 결정사항을 업데이트한다.
> 마지막 업데이트: <YYYY-MM-DD> (<어느 스킬이>)

## 파이프라인 상태

- [x] 0. kickoff — <날짜>
- [ ] 1. scaffold (`/gapp:scaffold`)
- [ ] 2. design (`/gapp:design`)
- [ ] 3. backend (`/gapp:backend`)        ← 불필요 시 "N/A(로컬 전용)"으로 표기
- [ ] 4. cicd (`/gapp:cicd`)
- [ ] 5. landing (`/gapp:landing`)
- [ ] 6. store-assets (`/gapp:store-assets`)
- [ ] 7. store-submit (`/gapp:store-submit`)

## 결정사항

### 프로덕트
- 한 줄 정의:
- 타깃 유저 / 첫 유저 확보:
- v1 코어 루프:
- v1에서 뺀 것(이후 목록):
- 이름 / 번들ID / 언어:

### 스택 (kickoff 시점 최신 조회 결과)
- Expo SDK: <N> (RN <x>, React <y>) — 조회일 <날짜>
- 플랫폼: iOS / Android / 웹
- 네이티브 기능 → dev client 필요: 예/아니오
- 백엔드: Supabase / 없음
- 로그인: 익명우선+승격 / …
- 과금: 없음 / …

### 디자인 방향 (상세는 DESIGN.md — design이 생성)
- 레퍼런스 / 무드 키워드:

## 운영 메모
- Apple Developer / EAS / Supabase 계정 상태:
- 테스트 경로: 시뮬레이터 → TestFlight 내부 → 심사
- 배포: main push=OTA, v* 태그=네이티브 빌드 (cicd 세팅 후 유효)
- 릴리스 전 게이트: `/gapp:preflight`

## 로그
- <날짜> kickoff 완료: <핵심 결정 한 줄>
```

**문서 규율 (모든 gapp 스킬 공통):** 단계를 완료한 스킬은 ① 체크박스 체크 ② 결정사항 갱신
③ 로그 한 줄 추가를 반드시 한다. 결정이 뒤집히면 지우지 말고 로그에 "변경: A→B (이유)"로 남긴다.

## 3부 — 마무리 + 이어달리기

유저에게 짧게 요약한다:
1. 확정된 결정 요약 (표 하나)
2. 테스트/배포가 앞으로 어떻게 굴러가는지 3~4줄 (시뮬레이터→TestFlight→심사 / OTA vs 빌드)

그리고 **멈추지 말고 `/gapp:scaffold`를 바로 이어서 실행한다** (이어달리기 규칙). 유저가 "오늘은
여기까지" 류의 신호를 준 경우에만 멈추고, 그때는 재개 명령(`/gapp:next`)을 알려준다.

## 피할 것

- 인터뷰를 건너뛰고 바로 코드 만들기 — 이 스킬의 존재 이유가 결정을 먼저 확정하는 것이다.
- 질문 10개를 한 번에 던지기 — 오피스아워는 대화지 설문이 아니다.
- 스택 버전을 기억으로 적기 — 반드시 그 자리에서 최신 조회.
- HARNESS.md 없이 종료 — 이 문서가 없으면 이후 스킬들이 전부 미아가 된다.
- 요약만 하고 멈추기 — 이어달리기 규칙 위반.
